# Computer Science, Built — Part 43: APIs and Services

Part 43 of a sixty-one-part course in computer science (see [the series plan](../README.md) and
[the syllabus](../SYLLABUS.md)), the fourth part of Act VIII, *Building Software*. Once a program is split across
machines, every function call becomes a message that can be lost, duplicated, delayed or reordered, and a remote call
can never be made to look exactly like a local one. Industry's answers have real mathematics underneath: schema
evolution as subtyping, idempotency, exactly-once as at-least-once plus deduplication, sagas in place of distributed
locks, and backpressure. We split the Job into three services and keep its counts exact while the network loses and
duplicates messages.

The instruments are in `explainer/cs/api/` (tested in `tests/test_cs43_api.py`):
* `wire.py`: Protocol Buffers' wire format from first principles (varints, zigzag, tags and wire types,
  length-delimited and packed fields), an encoder and a schemaless decoder, checked byte for byte against the examples
  in the published encoding guide; JSON's integers read as IEEE doubles; one record as JSON and as protobuf; a
  schema-compatibility checker (fields matched by number, required and optional, the varint family) run on seven
  schema changes.
* `delivery.py`: a network that loses, duplicates and delays messages; at-most-once, at-least-once and exactly-once
  increments of a counter; a breadth-first model checker that explores every execution of retry-until-acknowledged,
  with and without deduplication; the Job as three services (tokenize, count, rank), with and without idempotency
  keys; offset against cursor pagination under concurrent inserts; a retry storm under immediate retries, exponential
  backoff with jitter, and a gRPC-style retry budget.
* `services.py`: the dual-write problem against a transactional outbox; an order saga with compensations under
  injected failures; fan-out latency over a call graph and a deadline propagated down a call chain; an M/M/1 queue,
  unbounded and bounded; GraphQL's N + 1 queries and batching; visibility timeouts and dead-letter queues; a JWT
  verifier that trusts the header and one that pins the algorithm; clock pitfalls computed with `zoneinfo`;
  client-side load balancing (random, round robin, two choices, least loaded).

## Chapters

* **Hook.** The eight fallacies of distributed computing (Deutsch's seven of 1994, building on Joy and Lyon's, and
  Gosling's eighth), and three outages matched to them: GitHub's 43-second partition in October 2018 (the network is
  not reliable), Mirai against Dyn in October 2016 (not secure), Facebook's withdrawn backbone routes in October 2021
  (topology changes). The Job in three services: 353 messages of counts over a network that loses 5% and duplicates
  2%; with retries and no keys *the* is counted 2,924 times instead of 2,733 and 1,403 of 5,882 words are wrong
  (5,400 counts too many); with idempotency keys, none.
* **1. Calls across a network.** Birrell and Nelson's stubs (Xerox PARC, 1984; generated by Lupine): marshal, send,
  unmarshal, dispatch. Waldo et al.'s four reasons remote is not local (1994): latency (a local call takes
  nanoseconds; in our model a remote one takes 10 ms at the median and 30 ms at the 99th percentile, 10⁶ to 10⁷ times
  longer); no shared memory (one object passed twice arrives as two copies); concurrency; and partial failure (request
  lost, server crashed after the work, reply lost: the same silence). The two generals again (Part 38): an RPC system
  runs a call at most once or at least once. Interface description languages and stub generators, from Sun RPC (1988)
  through CORBA and Thrift to gRPC (2015), whose calls take a deadline and return a status.
* **2. Bytes on the wire.** JSON's numbers as doubles: every integer up to 2⁵³ is exact, beyond it only every second
  one, so 2⁵³ + 1 arrives as 2⁵³ and the id 1234567890123456789 is read as 1234567890123456768 (doubles there are 256
  apart); RFC 8259's warning. Varints derived on 150 (`96 01`): one byte up to 127, one more for every seven bits, ten
  for 2⁶³. Tags as `field << 3 | wire type`; `{a: 150}` is `08 96 01`, the string *testing* is `12 07` and seven
  bytes; our encoder reproduces all eight of the guide's examples. Zigzag: −2 takes ten bytes as an int32 and one
  (`03`) as an sint32; −1000 takes two rather than ten; the guide's table matched at the extremes. One record: 90
  bytes of JSON against 34 of protobuf, and the bytes mean nothing without the schema.
* **3. Schemas that evolve.** Rolling deploys and old data: backward compatibility (new code reads old data) and
  forward compatibility (old code reads new data). Compatibility as width subtyping (Part 14). Seven changes checked:
  adding or removing an optional field is safe both ways; adding a required field breaks backward compatibility,
  removing one breaks forward compatibility; changing a type breaks both; widening int32 to int64 passes (an old
  reader truncates large values); renumbering passes both ways, and is a trap: a count of 1226 written as field 2
  (`10 ca 09`) and read as field 5 becomes 0, with nothing failing; `reserved` numbers and names; proto3 has no
  required fields. Avro (2009) resolves the writer's and reader's schemas by name, with defaults, so its dangerous
  change is a rename. Zero-copy formats (Cap'n Proto, FlatBuffers): an offset table, one jump, read in place.
* **4. API styles.** REST (Fielding 2000): resources, representations, a uniform interface, statelessness. RFC 9110's
  safe and idempotent methods (PATCH need not be idempotent); a PUT sent twice leaves the cart as intended, a POST sent
  twice places a second order. Offsets against cursors on 1,000 rows in pages of 50: with 0, 1, 3 and 10 new rows per
  page, offsets repeat 0, 20, 63 and 240 rows and scan 10,500, 11,520, 12,613 and 16,240; cursors repeat none and
  scan 1,000. gRPC (2015, from Stubby): unary, server-streaming, client-streaming and bidirectional calls over HTTP/2.
  GraphQL (2015): 50 authors and their books cost 51 queries naively (251 with each book's reviews) and 2 (3) with
  DataLoader-style batching; persisted queries and cost limits.
* **5. At most, at least, exactly once.** Three promises. 10,000 increments over a network that loses 5% of messages,
  acknowledgements included, and duplicates 2%: at most once counts 9,694 (306 lost), at least once 10,754 (754
  extra), exactly once 10,000; the last two send the same 21,841 messages in four rounds of retries, so deduplication
  costs no traffic. A model checker visits every state of two increments, each sent up to three times: 4,319 states
  with deduplication, in none of which the counter exceeds 2; 9,579 without, with a shortest violation six steps from
  the start (send three times, deliver three times: counter 3). One resend each, 1 to 4 increments: 47, 1,053, 21,963
  and 442,169 states (×22, ×21, ×20). The theorem, proved under fairness. Idempotency keys in payment APIs:
  exactly-once delivery is impossible, exactly-once processing is not.
* **6. Designing and versioning APIs.** Hyrum's law as a model: if each of N consumers relies on an incidental
  behaviour with probability p, somebody does with probability 1 − (1 − p)^N, passing one half at N ≈ 0.69/p (69, 693
  and 6,931 consumers for p = 0.01, 0.001, 0.0001). Changes that break and changes that don't (a new enumeration value
  only looks additive). Versions, deprecation and the Sunset header (RFC 8594, 2019); versions in the path or in a
  header, major numbers only. Google's resource-oriented design: five standard methods per collection and custom
  methods after a colon. Consumer-driven contract tests (Pact): renaming `author.name` fails the mobile app's
  contract. Postel's robustness principle (RFC 793, 1981) against RFC 9413 (2023).
* **7. Queues and pub/sub.** A queue decouples producer and consumer in time and in rate (SQS, RabbitMQ, Kafka, Cloud
  Pub/Sub; Hohpe and Woolf, 2003). Receive, hide, delete: a 30-second visibility timeout outlived by a slow worker, so
  the work is done twice. Poison messages go to a dead-letter queue after five receives; of 2,000 simulated messages,
  98 were processed more than once (153 extra receives, 2,161 in all) and 2 were dead-lettered. Publish and subscribe;
  Kafka's partitioned log (2011): order per key, consumer groups and committed offsets.
* **8. Backpressure.** An M/M/1 queue in front of a service: mean time in system 2.0, 5.3, 11.4, 23.7 and 107
  service times at loads 0.5 to 0.99, against 1/(1 − ρ) = 2, 5, 10, 20, 100; above load 1 no steady state (1,451 and
  4,401 after 50,000 arrivals at 1.05 and 1.2). Bounded at 20, the mean stays under 16 at every load, at the price of
  shedding 0.3% of requests at load 0.8 and 17.2% at 1.2. A retry storm (capacity 100/s, demand 90/s, down from 20 to
  30 s): immediate retries peak at 990/s and recover at 119 s; backoff with jitter peaks at 381/s and recovers at 69 s;
  a retry budget (gRPC's throttling) retries only 49 failures, peaks at 139/s and recovers at 31 s, but gives up on
  900 requests. Metastable failures (Bronson et al., 2021); circuit breakers (Nygard, 2007), load shedding, admission
  control and deadlines.
* **9. Monoliths and microservices.** What a split gains (teams that deploy and scale on their own; Conway's law,
  Part 40) and costs. Bounded contexts (Evans, 2003) and the distributed monolith. Fan-out to k back ends, 20,000
  simulated requests each: for k = 1, 5, 20, 100 the median is 21, 26, 31 and 85 ms, the 99th percentile 150, 198, 213
  and 226 ms, and 1.7%, 4.4%, 12.1% and 46.4% of requests take over 100 ms, against 1 − 0.99^k = 1.0%, 4.9%, 18.2% and
  63.4% (one back end alone: median 10 ms, 99th percentile 30 ms). A 150 ms deadline down a call chain: gateway 5 ms,
  auth 8 (with 145 left), orders 25 (137), inventory 30 (112), payments 60 (82), and 22 ms of slack.
* **10. Data across services.** A database per service and the dual-write problem: 10,000 orders with a 1% crash
  between the writes; commit then publish loses 110 events, publish then commit commits 9,890 and announces 110
  phantom orders; the transactional outbox loses none and invents none, at the price of 110 harmless duplicates;
  change data capture (Debezium, Part 46). Sagas (Garcia-Molina and Salem, 1987): reserve stock, charge card, book
  courier, send confirmation, with compensations run in reverse; one order fails at the courier and is refunded and
  released. 10,000 sagas: 9,359 completed, 641 compensated (106 at the stock step, 317 at the charge, 218 at the
  courier), 57 compensations retried, 0 orders left half done. No isolation (semantic locks, commutative updates);
  orchestration and choreography; why not two-phase commit (Part 39).
* **11. Finding, routing and trusting services.** Registries, health checks and DNS. The power of two choices, with
  50 servers at 90% load (time in system in service times, mean and 99th percentile): random 10.1 and 48.8, round
  robin 4.8 and 21.0, two choices 2.6 and 9.1, least loaded 1.2 and 5.2; ln n/ln ln n against ln ln n/ln 2 (Azar,
  Broder, Karlin and Upfal, 1994). Sidecars and the service mesh (Envoy, Istio, Linkerd), mutual TLS (Part 30) and
  SPIFFE identities. OAuth 2.0's authorization-code flow with PKCE. JWTs: our naive verifier rejects an edited payload
  but accepts an `alg: none` token claiming admin; the verifier that pins HS256 (RFC 8725) rejects both forgeries.
  Macaroons (Birgisson et al., 2014): caveats chained by HMAC, so a holder can only weaken a token (Part 55).
* **12. Time in APIs.** Wall clock against monotonic clock (an illustrative −0.7 s duration). New York on 8 March
  2026: 01:30 EST plus one wall-clock hour is 02:30, which does not exist; normalised through UTC it is 03:30 EDT, one
  real hour later. Lord Howe Island is UTC+10:30, with a half-hour shift. 27 leap seconds since 1972, the 2012 leap
  second, Google's smear, and the 2022 decision to stop by 2035. 2³¹ − 1 = 2,147,483,647 seconds is
  2038-01-19T03:14:07Z, and one second later a signed 32-bit clock reads 1901-12-13T20:45:52Z. Five rules for time in
  an API; an idempotency key expiring early on a clock two minutes fast (illustrative).
* **13. The Job as three services.** The first 70,588 words of the novels in 353 chunks of 200 words: 772 messages,
  39 lost, 22 duplicated, three rounds of retries. As loss and duplication rise from 0%/0% to 20%/10%, the counter
  without keys gets 0, 504, 1,403, 1,880 and 2,890 of the 5,882 words wrong (0, 1,200, 5,400, 9,600 and 23,200 counts
  too many: every error is an over-count); with keys, none, and only the traffic grows (706 to 992 messages). What
  the counter remembers: 353 keys, recorded atomically with the counts; time-to-live or sequence numbers; Kafka's
  idempotent producers. The end-to-end argument (Saltzer, Reed and Clark, 1984): TCP's guarantee ends at the socket.
* **14. Frontier: services you can prove.** Protocols as types: a global choreography projected onto each service
  (session types, Honda 1993; multiparty, Honda, Yoshida and Carbone 2008; choreographic programming, Montesi).
  Checking every execution: 47 states for one message, 442,169 for four; TLA⁺ at Amazon (Newcombe et al., 2015);
  IronFleet (Dafny) and Verdi (Coq), 2015. Testing the whole system: FoundationDB's deterministic simulation, Jepsen,
  chaos engineering. Four open problems and the ★ research problem.
* **Outro.** Recap, payoffs, practice, problems, next part.

## Problems, with solutions

1. **Varints by hand.** Encode the message `{a: 300, b: -3, c: [1, 2]}` by hand (`a` an int32, `b` an sint32, `c`
   packed), and decode it back.

   *Solution.* Number the fields 1, 2 and 3, as in the encoding guide. *a*: 300 = 1 0010 1100₂; the low seven bits
   are 010 1100 = 0x2C, sent first with the continuation bit set (0xAC), then the remaining bits, 10₂ = 0x02. The tag
   is 1 << 3 | 0 = 0x08, so *a* is `08 AC 02`. *b*: zigzag maps −3 to (−3 << 1) ^ (−3 >> 31) = 5, a one-byte varint;
   the tag is 2 << 3 | 0 = 0x10, so *b* is `10 05`. *c*: a packed field is length-delimited, tag 3 << 3 | 2 = 0x1A,
   then the length of the payload, 2, then the varints 1 and 2: `1A 02 01 02`. The message is
   `08 AC 02 10 05 1A 02 01 02`, nine bytes (the compact JSON `{"a":300,"b":-3,"c":[1,2]}` is 26). Decoding: `08` is
   key 8, field 8 >> 3 = 1, wire type 8 & 7 = 0, a varint; `AC 02` gives 0x2C + (0x02 << 7) = 44 + 256 = 300. `10` is
   field 2, wire type 0; `05` unzigzags to (5 >> 1) ^ −(5 & 1) = 2 ^ −1 = −3. `1A` is field 3, wire type 2; the length
   `02` covers `01 02`, the varints 1 and 2. Had *b* been an int32, −3 would have gone as its 64-bit two's complement,
   ten bytes (`FD FF FF FF FF FF FF FF FF 01`), and the message would be 18 bytes. Our `wire.encode` and `wire.decode`
   give exactly these bytes and fields.

2. **Compatibility as subtyping.** Show that adding an optional field is backward and forward compatible, and that
   changing a field's type is neither, by treating messages as records and compatibility as subtyping.

   *Solution.* Treat a schema as a record type: a finite map from field numbers to a type and a flag, required or
   optional. A reader with schema R can read data written with schema W when W <: R in the following sense: for every
   field n of R, if n is in W then W's type for n is a subtype of R's (depth), and if n is required in R then n is in
   W and required there; fields of W that R lacks are skipped (width). Backward compatibility of a change v1 → v2 is
   v1 <: v2 (new code reads old data); forward compatibility is v2 <: v1 (old code reads new data). Let v1 =
   {1: word string required, 2: count int64 optional} and v2 = v1 + {3: novel string optional}. Forward: every field
   of v1 is in v2 with the same type and flag, and field 3 is extra, so v2 <: v1 by width subtyping; the old reader
   skips field 3 (protobuf keeps its bytes). Backward: v1 lacks field 3, but field 3 is optional in v2, so the
   condition holds and the new reader gives `novel` its default; v1 <: v2. Now let v2 change field 2 to a string.
   The fields share a number, so depth subtyping needs int64 <: string or string <: int64, and neither holds: there is
   no value of one type that is a value of the other. Both directions fail, which is what our checker reports
   ("int64 written, read as string; and the reverse"). On the wire the tag itself changes, from `10` (wire type 0) to
   `12` (wire type 2), so a reader cannot interpret the bytes as its type at all: depending on the implementation the
   value is dropped or decoding fails. (Our checker treats int32, int64, uint32, uint64 and bool as one varint family,
   which is why widening int32 to int64 passes; the narrow reader then truncates values that no longer fit.)

3. **Exactly once.** Prove that retrying until acknowledged, with a receiver that applies each id at most once,
   delivers every message exactly once if the network eventually delivers some copy.

   *Solution.* The sender has messages with distinct ids 1, …, n and resends each id until it receives an
   acknowledgement for it. The receiver keeps a set A of applied ids and a counter c; on receiving a copy of i it
   applies i and adds i to A in one atomic step if i ∉ A, and in either case sends an acknowledgement of i. Fairness:
   a message sent infinitely often (in either direction) is eventually delivered. *At most once.* Initially c = 0 and
   A = ∅. Every step that increments c also adds a new element to A, and no step does one without the other, so
   c = |A| always; an id joins A only if it was absent, so each id is applied at most once, and A ⊆ {1, …, n} gives
   c ≤ n in every state, whatever the network does. *At least once.* Suppose some i is never applied. Then no copy of
   i ever arrives (an arriving copy either applies i or finds it in A). Acknowledgements of i are sent only when a copy
   arrives, so none is ever sent, the sender never hears one, and it sends i infinitely often; by fairness a copy is
   delivered, a contradiction. So every id is eventually in A and c = n. *Termination.* Once i is applied, every
   further copy of i that arrives is acknowledged; if the sender went on resending i for ever, infinitely many copies
   would arrive (fairness), infinitely many acknowledgements would be sent, and fairness again delivers one, after
   which the sender stops. Duplication and reordering change nothing in the argument, since it never counts copies.
   The atomicity matters: if a crash could fall between applying i and recording it, a later copy would be applied
   again. Chapter 5's model checker, whose resends are bounded and so cannot assume fairness, checked the conditional
   form (if both increments were acknowledged the counter is 2, and it never exceeds 2) in all 4,319 states; without
   deduplication it found a violation in six steps, with the counter at 3.

4. **Offsets and cursors.** Show that offset pagination over a list receiving k inserts per page repeats about k rows
   per page, and that cursor pagination repeats none.

   *Solution.* The list is sorted newest first, pages hold p rows, and k ≤ p new rows arrive at the top after each
   page is read. *Offset.* Page j (from 0) asks for positions jp to jp + p − 1. By then jk rows have been inserted
   above the original ones, so an original row at position r now sits at r + jk, and page j shows the original rows
   jp − jk to jp − jk + p − 1 (no new row appears, since jp ≥ jk). Page j − 1 showed the original rows
   (j − 1)(p − k) to (j − 1)(p − k) + p − 1. The overlap runs from j(p − k) to (j − 1)(p − k) + p − 1, which is
   exactly k rows: each page after the first repeats the last k rows of the one before, and the reader advances only
   p − k original rows per page. To cover n rows it needs P = ⌈n/(p − k)⌉ pages and sees k(P − 1) repeats. For
   n = 1,000 and p = 50 this gives P = 21, 22, 25 and 20, 63, 240 repeats for k = 1, 3, 10, exactly the simulated
   figures. No row is missed under inserts; under deletions the shift goes the other way and rows are skipped. The cost
   is quadratic, since the database steps past every skipped row: with no inserts, Σ (50j + 50) over j = 0, …, 19 =
   10,500 rows scanned, about n²/2p. *Cursor.* Page j asks for the p newest rows with id below the last id of page
   j − 1. Every new row has a larger id than every existing one, so it never satisfies the condition; the last id seen
   strictly decreases from page to page, so the pages are disjoint and together are the original list in order: no
   repeats, no misses, and with an index on id, p rows read per page (1,000 in all). A cursor needs a unique, totally
   ordered key; if the sort key can tie, the id breaks the tie.

5. **Build.** Add a saga to our simulator in which the courier step can time out, and show that an idempotent
   compensation keeps the invariant.

   *Solution sketch.* A timeout is the third outcome of chapter 1's partial failure: the booking may or may not have
   happened, or may still happen when a delayed request arrives. Extend `services.saga_run` with a `timeout_at` step
   and a hidden coin for whether the courier service actually booked; on a timeout the saga must treat the step as
   possibly done and compensate it too, in reverse order: cancel courier, refund card, release stock. Give the courier
   service a table keyed by the order's idempotency key: `book(key)` records a booking unless the key is already
   marked cancelled, and `cancel(key)` marks it cancelled whether or not a booking exists, so that cancel is
   idempotent, harmless when nothing was booked, and wins over a booking request that arrives after it (deliver the
   delayed request with `delivery.Net` to test that case). Compensations are retried until they succeed, as in
   `saga_experiment` (`comp_fail`), so each must be idempotent: a refund keyed by the order, not one refund per
   attempt. Check the invariant on every order at the end of the run, against the services' own state rather than the
   saga's log: either stock reserved, card charged, courier booked and confirmation sent, or none of them in effect. A
   complete answer runs it twice over many orders with a timeout probability of a few percent: with the idempotent
   compensations no order is left inconsistent; with a non-idempotent refund every retried refund pays out twice, and
   with a cancel that does not record a tombstone a late booking leaves a courier booked for a refunded order, and the
   checker counts both.

6. **★ Research.** A compatibility checker proving that every existing client completes every protocol run against a
   new version, under loss, duplication and reordering.

   *Discussion.* Open. Chapter 3's checker compares message types, but compatibility that matters is behavioural: a
   new version can keep every type and still change the order of messages, add a state, or turn a call that was safe
   to retry into one that is not. Behavioural compatibility is a subtyping question about protocols, and even
   session-type subtyping over asynchronous (unboundedly buffered) channels is known to be undecidable in general
   (Bravetti, Carbone and Zavattaro; Lange and Yoshida, 2017); loss, duplication and reordering only enlarge the set of
   runs, and the "existing clients" are programs written by strangers, known only through their traffic or their
   contracts (Hyrum's law). A good partial answer would fix a model (finite-state clients, for instance extracted from
   consumer-driven contracts; services as session types), reduce lossy and duplicating channels to reliable reordering
   ones for protocols whose effects are deduplicated (chapter 5's theorem, made a lemma), and give a checker that is
   sound and decidable on a stated fragment, such as bounded buffers or protocols without loops, with a proof that it
   accepts the safe changes of chapters 3 and 6 and rejects the renumbering trap and a new enumeration value a client
   cannot handle. A cutoff result (a bound on buffer size or on the number of retries beyond which nothing new
   happens), or an evaluation on the history of a real public API, would also be new.

## 习题与解答

1. **手算变长整数。** 手工编码消息 `{a: 300, b: -3, c: [1, 2]}`（`a` 为 int32，`b` 为 sint32，`c` 为打包字段），再把它解码回来。

   *解答。* 按编码指南的惯例，三个字段编号为 1、2、3。*a*：300 = 1 0010 1100₂；低七位 010 1100 = 0x2C 先发送，并置上延续位
   （0xAC），然后是余下的位 10₂ = 0x02。标签为 1 << 3 | 0 = 0x08，所以 *a* 是 `08 AC 02`。*b*：之字形编码（zigzag）把 −3 映射为
   (−3 << 1) ^ (−3 >> 31) = 5，是一个字节的变长整数；标签为 2 << 3 | 0 = 0x10，所以 *b* 是 `10 05`。*c*：打包字段带长度前缀，标签
   3 << 3 | 2 = 0x1A，然后是载荷长度 2，再是变长整数 1 和 2：`1A 02 01 02`。整条消息是 `08 AC 02 10 05 1A 02 01 02`，共九个字节（紧凑的
   JSON `{"a":300,"b":-3,"c":[1,2]}` 是 26 个字节）。解码：`08` 是键 8，字段 8 >> 3 = 1，线路类型 8 & 7 = 0，即变长整数；`AC 02` 得
   0x2C + (0x02 << 7) = 44 + 256 = 300。`10` 是字段 2、线路类型 0；`05` 反向之字形解码为 (5 >> 1) ^ −(5 & 1) = 2 ^ −1 = −3。`1A` 是字段
   3、线路类型 2；长度 `02` 覆盖 `01 02`，即变长整数 1 和 2。如果 *b* 是 int32，−3 就要按 64 位补码发送，占十个字节
   （`FD FF FF FF FF FF FF FF FF 01`），整条消息变成 18 个字节。我们的 `wire.encode` 和 `wire.decode` 给出的正是这些字节和字段。

2. **兼容性即子类型。** 把消息看作记录、把兼容性看作子类型关系，证明增加一个可选字段既向后兼容又向前兼容，而改变一个字段的类型两者都不是。

   *解答。* 把模式（schema）看作一个记录类型：从字段编号到“类型和标志（必需或可选）”的有限映射。读取方模式为 R、写入方模式为 W 时，
   读取方能读 W 写的数据，当且仅当在如下意义下 W <: R：对 R 的每个字段 n，若 n 在 W 中，则 W 中 n 的类型是 R 中类型的子类型（深度）；
   若 n 在 R 中是必需的，则 n 在 W 中存在且也是必需的；W 有而 R 没有的字段被跳过（宽度）。变更 v1 → v2 向后兼容即 v1 <: v2（新代码读旧数据），
   向前兼容即 v2 <: v1（旧代码读新数据）。设 v1 = {1: word string 必需, 2: count int64 可选}，v2 = v1 + {3: novel string 可选}。向前：v1 的每个
   字段都以相同的类型和标志出现在 v2 中，字段 3 是多出来的，所以由宽度子类型 v2 <: v1；旧的读取方跳过字段 3（protobuf 保留它的字节）。
   向后：v1 没有字段 3，但字段 3 在 v2 中是可选的，条件成立，新的读取方给 `novel` 取默认值；v1 <: v2。现在让 v2 把字段 2 改成 string。
   两个字段编号相同，深度子类型要求 int64 <: string 或 string <: int64，两者都不成立：一种类型的值都不是另一种类型的值。两个方向都失败，
   这正是我们的检查器报告的（“int64 written, read as string; and the reverse”）。在线路上标签本身也变了，从 `10`（线路类型 0）变成 `12`
   （线路类型 2），所以读取方根本无法按自己的类型解释这些字节：视实现而定，这个值被丢弃，或者解码失败。（我们的检查器把 int32、int64、
   uint32、uint64 和 bool 视为同一个变长整数家族，所以把 int32 放宽为 int64 能通过；窄的读取方随后会截断放不下的值。）

3. **恰好一次。** 证明：在重试直到收到确认、且接收方对每个 id 至多应用一次的条件下，只要网络最终会投递某个副本，每条消息都恰好被投递一次。

   *解答。* 发送方有 id 互不相同的消息 1, …, n，对每个 id 不断重发，直到收到它的确认。接收方维护已应用 id 的集合 A 和计数器 c；收到 i 的
   一个副本时，若 i ∉ A，就在一个原子步骤中应用 i 并把 i 加入 A；无论哪种情况都发送 i 的确认。公平性：（任一方向上）被发送无穷多次的消息
   最终会被投递。*至多一次。* 初始时 c = 0、A = ∅。每个使 c 加一的步骤也向 A 加入一个新元素，没有哪个步骤只做其一，所以始终 c = |A|；
   一个 id 只有在不在 A 中时才加入 A，所以每个 id 至多被应用一次，而 A ⊆ {1, …, n} 给出在每个状态下 c ≤ n，无论网络做什么。*至少一次。*
   假设某个 i 从未被应用。那么 i 的副本从未到达（到达的副本要么应用 i，要么发现它已在 A 中）。i 的确认只在副本到达时才发送，所以从未发送过，
   发送方从未收到确认，于是无穷多次发送 i；由公平性，某个副本被投递，矛盾。所以每个 id 最终都在 A 中，c = n。*终止。* i 被应用后，此后到达
   的每个 i 的副本都会被确认；如果发送方永远重发 i，就会有无穷多个副本到达（公平性），发出无穷多个确认，公平性再次保证其中一个被投递，之后
   发送方停止。重复和乱序在论证中不起作用，因为论证从不数副本。原子性是关键：如果崩溃可能发生在应用 i 和记录 i 之间，之后到达的副本就会被
   再次应用。第5章的模型检查器重发次数有界，不能假定公平性，所以它在全部 4,319 个状态中检查的是条件形式（如果两次递增都被确认，计数器就是
   2，而且从不超过 2）；不去重时，它在六步之内找到一个违例，计数器为 3。

4. **偏移与游标。** 证明：在每页之间插入 k 行的列表上，偏移分页每页大约重复 k 行，而游标分页一行也不重复。

   *解答。* 列表按从新到旧排序，每页 p 行，每读完一页就有 k ≤ p 个新行出现在顶部。*偏移。* 第 j 页（从 0 起）请求位置 jp 到 jp + p − 1。
   此时原有各行之上已经插入了 jk 行，所以原来位于位置 r 的行现在位于 r + jk，第 j 页显示的是原来的第 jp − jk 到 jp − jk + p − 1 行（不会出现
   新行，因为 jp ≥ jk）。第 j − 1 页显示的是原来的第 (j − 1)(p − k) 到 (j − 1)(p − k) + p − 1 行。重叠部分从 j(p − k) 到
   (j − 1)(p − k) + p − 1，恰好 k 行：第一页之后的每一页都重复前一页的最后 k 行，读者每页只前进 p − k 个原有行。覆盖 n 行需要
   P = ⌈n/(p − k)⌉ 页，看到 k(P − 1) 次重复。对 n = 1,000、p = 50，k = 1、3、10 时 P = 21、22、25，重复 20、63、240 行，与模拟结果完全
   一致。插入时不会漏掉行；删除时位移方向相反，就会跳过行。代价是平方级的，因为数据库要逐行越过每个被跳过的行：没有插入时，对
   j = 0, …, 19 求和 Σ (50j + 50) = 10,500 行，约为 n²/2p。*游标。* 第 j 页请求 id 小于第 j − 1 页最后一个 id 的最新 p 行。每个新行的 id 都比
   所有已有行大，所以永远不满足条件；看到的最后一个 id 逐页严格递减，所以各页互不相交，合起来正是按顺序排列的原列表：没有重复，没有遗漏；
   若 id 上有索引，每页只读 p 行（共 1,000 行）。游标需要一个唯一且全序的键；若排序键可能相等，就用 id 打破平局。

5. **动手。** 给我们的模拟器加一个 saga（长事务），其中订快递一步可能超时，并说明幂等的补偿能保持不变量。

   *解答要点。* 超时是第1章部分失败的第三种结果：预订可能发生了，也可能没有，还可能在一个延迟的请求到达时才发生。给 `services.saga_run`
   加一个 `timeout_at` 步骤，以及一枚隐藏的硬币决定快递服务是否真的订上了；超时时 saga 必须把这一步视为可能已完成，也要补偿它，按相反顺序：
   取消快递、退款、释放库存。给快递服务一张以订单的幂等键为键的表：`book(key)` 记录一次预订，除非该键已被标记为取消；`cancel(key)` 无论预订
   是否存在都把它标记为取消。这样取消是幂等的，在什么也没订时无害，并且能压过在它之后才到达的预订请求（用 `delivery.Net` 投递延迟的请求来
   测试这种情形）。补偿会重试直到成功，就像 `saga_experiment`（`comp_fail`）中那样，所以每个补偿都必须幂等：退款以订单为键，而不是每次尝试
   退一笔。运行结束时对每个订单检查不变量，依据各服务自己的状态而不是 saga 的日志：要么库存已预留、卡已扣款、快递已预订、确认已发送，要么
   这些都不生效。完整的答案在许多订单上、以几个百分点的超时概率运行两次：使用幂等补偿时，没有订单处于不一致状态；使用不幂等的退款时，每次
   被重试的退款都付出两次，而不记录墓碑（tombstone）的取消会让迟到的预订给一个已退款的订单留下一辆快递，检查器把这两种情况都数出来。

6. **★ 研究。** 一个兼容性检查器，证明在丢失、重复和乱序之下，每个现有客户端在新版本上都能完成每一次协议运行。

   *讨论。* 尚未解决。第3章的检查器比较的是消息类型，但真正要紧的是行为上的兼容：新版本可以保持每一个类型不变，却改变消息的顺序、增加一个
   状态，或者把一个可以安全重试的调用变成不可以的。行为兼容是关于协议的子类型问题，而即使是异步（缓冲无界）信道上的会话类型子类型，一般而言
   也已知是不可判定的（Bravetti、Carbone 与 Zavattaro；Lange 与 Yoshida，2017）；丢失、重复和乱序只会扩大运行的集合，而“现有客户端”是
   陌生人写的程序，只能通过它们的流量或契约来了解（海勒姆定律）。好的部分答案应当固定一个模型（有限状态的客户端，例如从消费者驱动的契约中
   提取；服务表示为会话类型），对效果已去重的协议，把会丢失、会重复的信道归约为可靠但会乱序的信道（把第5章的定理变成一条引理），并给出一个
   在明确规定的片段上（例如有界缓冲，或者没有循环的协议）可靠且可判定的检查器，证明它接受第3章和第6章中安全的变更，拒绝重新编号的陷阱，
   以及客户端无法处理的新枚举值。一个截断结果（缓冲大小或重试次数的一个界，超过它就不会出现新情况），或者在一个真实公开 API 的历史上做的
   评估，也都是新的。

## Glossary additions

* **fallacies of distributed computing** — eight false assumptions about networks (reliable, zero latency, infinite
  bandwidth, secure, fixed topology, one administrator, free transport, homogeneous).
* **remote procedure call (RPC), stub, marshalling, interface description language (IDL)** — a call to a procedure
  on another machine made to look local; the generated local stand-ins; turning arguments into bytes; the language in
  which an interface is written once.
* **partial failure, timeout** — one part of a system failing while the rest runs; the only signal a caller gets.
* **varint, zigzag encoding, tag, wire type, length-delimited, packed field** — Protocol Buffers' integers, seven bits
  per byte; interleaving signs so small negatives stay short; a field number and wire type in one varint; a length
  followed by bytes; a repeated scalar sent as one length-delimited field.
* **schema evolution, backward and forward compatibility, width subtyping, reserved field** — changing a format while
  old and new code coexist; new code reading old data and old code reading new; a record with more fields standing
  for one with fewer; a retired field number that may never be reused.
* **writer's and reader's schema, schema resolution, schema registry** — Avro's pair of schemas matched by name.
* **zero-copy format** — bytes on the wire laid out as the program uses them, read in place through offsets.
* **REST, resource, representation, uniform interface, statelessness** — Fielding's architectural style for the web.
* **safe and idempotent methods** — HTTP methods that request no change; those whose repetition has the effect of one.
* **offset and cursor (keyset) pagination** — skipping k rows; asking for the rows after the last one seen.
* **gRPC, unary and streaming calls, deadline, status** — typed procedure calls over HTTP/2.
* **GraphQL, resolver, N + 1 problem, batching (DataLoader), persisted query** — a client-shaped query language; the
  per-field functions that fill a response; one query per parent; collecting keys into one query; a query registered
  in advance by its hash.
* **at-most-once, at-least-once and exactly-once semantics, deduplication, idempotency key** — how often a message
  takes effect; remembering ids already applied; a client-chosen id for one intended operation.
* **model checking, fairness** — exploring every reachable state of a model; the assumption that what is sent often
  enough is eventually delivered.
* **Hyrum's law, additive change, deprecation, Sunset header, consumer-driven contract test** — every observable
  behaviour has dependants; changes nobody could have observed; announcing retirement; a dated end of service; tests
  in which consumers state what they rely on.
* **robustness principle** — Postel's "be liberal in what you accept", and its critique in RFC 9413.
* **message queue, visibility timeout, dead-letter queue, poison message** — a buffer between services; how long a
  received message stays hidden; where messages that keep failing are set aside; a message that always fails.
* **publish/subscribe, topic, subscription, partition, consumer group, offset** — delivery to every subscriber;
  Kafka's ordered log per key and the position each consumer has read to.
* **backpressure, load shedding, admission control, bounded queue** — pushing overload back to the sender.
* **retry storm, exponential backoff, jitter, retry budget, metastable failure** — retries that amplify an outage;
  waits that double; randomised waits; a cap on retries; an overload that sustains itself.
* **circuit breaker (closed, open, half-open)** — failing fast on calls to a sick dependency.
* **monolith, microservice, bounded context, distributed monolith** — one deployable program; many; a part of the
  business with its own model; services that must still deploy together.
* **fan-out, tail latency, latency budget, deadline propagation** — one request becoming many; the slowest of them;
  dividing a deadline down a call chain.
* **dual-write problem, transactional outbox, change data capture (CDC)** — two writes with no transaction spanning
  them; an event row committed with the data; publishing a database's own log of changes.
* **saga, compensation, orchestration, choreography, semantic lock** — a long transaction as local steps with undos;
  a semantic undo; a coordinator or services reacting to events; marking data as pending.
* **service discovery, health check, power of two choices** — finding healthy instances; sending each request to the
  less loaded of two random servers.
* **sidecar, service mesh, control plane, mutual TLS, workload identity (SPIFFE)** — a proxy beside each service;
  the proxies together; their configuration; TLS with certificates on both sides; a name for a service in its
  certificate.
* **OAuth 2.0, authorization code, PKCE, access token, refresh token** — delegated access without sharing a password.
* **JSON Web Token (JWT), claims, `alg: none`, algorithm pinning** — a signed token of claims; an unsecured token the
  standard allows; a verifier that chooses the algorithm itself.
* **capability, bearer token, macaroon, caveat** — a token whose possession is the permission; one any holder can
  weaken by chaining HMACs over conditions.
* **wall clock, monotonic clock, time zone, UTC offset, daylight saving gap, leap second, smear, Year 2038 problem** —
  the date and time of day; a clock that only moves forwards; named rules for local time; a time that never occurs;
  an extra second in UTC and spreading it out; the overflow of a signed 32-bit Unix time.
* **end-to-end argument** — a function that needs the application's knowledge can only be completed at the endpoints.
* **session type, choreography, projection** — a protocol as a type; a global description of a conversation; each
  participant's local part of it.
